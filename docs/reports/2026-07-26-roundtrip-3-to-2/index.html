ラウンドトリップ削減 3 → 2

Abstract

What画面を1枚出すためのデータベース往復を、3回から2回に減らした。
WhyWorker は東京、データベースはシンガポール。往復1回あたり約70msが構造的にかかる。
Howアクセス権チェックが単独で発行していた「プロジェクト行の読み取り」を廃止した。同じ行は、後続のワークスペース一括読み取りがすでに取ってきていた。

変更前後のラウンドトリップ。3本とも逐次で、②が終わるまで③を出せなかった。

結果

  • 効いた — WBS 画面などの表示は 3往復 → 2往復。プロジェクト一覧からクリックしたときに通る素の /projects/:id（/wbs へ転送するだけの経路）は 2往復 → 1往復。保存の POST も往復が1本減った。
  • 効かなかった / 悪化した — /projects/:id/dashboard は、プロジェクト名ひとつを出すためにワークスペース全体（8クエリ）を読むようになった。往復回数は変わらないが読む量は増えた。実装待ちのスタブ画面なので、直さず債務として記録した（判断理由は仕組み）。
  • 残った制約 — 東京とシンガポールの間の約70msは物理的な下限で、これ以上は往復を減らすしかない。残り2往復は「誰か」を確定してからでないと「何を読んでよいか」が決まらないため、原理的に1本にはできない。

安全性は動かしていない

このコードは以前セキュリティレビューを受けた「アクセス拒否」の中核部分です。次の3つを変えないことが条件でした。 いずれも維持されています（検証／Fable の独立レビューでも確認）。

  • 拒否はミドルウェアで起き、子ローダーが1つも動く前に打ち切られる
  • 「メンバーでない」「存在しない」「IDの形式が不正」「行が消えた」はすべて同一の 404（本文まで同じ null）で、外部から区別できない
  • 拒否されたリクエストはプロジェクトのデータベースに一切触れない
ただし1点、正直に記録すべき差分があります。書き込み（保存 POST）だけは、削除済みプロジェクトに対する応答の本文がゲートの 404 と形が異なります。既存の形状で、今回はその発生窓が広がっただけです。直さなかった理由はリスクと残タスクに書きました。

判断が要ること

  • なし。この変更自体に、ユーザーの判断を要する点はありません。
  • ただし本番反映は main へのマージ → CI → 人間承認、という手順です。現在の変更はブランチ adr-0011-effort-wbs-realignment に push 済みで、本番には出ていません。
